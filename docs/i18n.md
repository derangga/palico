# Localization

Palico ships in English (`en`, the base locale) and Indonesian (`id`). Messages are
compiled by [Paraglide JS](https://paraglidejs.com) into typed functions. There is
no locale in the URL: the same page serves both languages.

## How the language is chosen

On first paint the app asks, in order:

1. The saved choice, in `localStorage` under `palico:locale`.
2. The browser language list (`navigator.languages`). The first entry whose primary
   subtag is a shipped locale wins, so `id-ID` gives `id`. The legacy Android code
   `in` also gives `id`.
3. English.

The choice never uses the person's IP address or location. It would need a server
or a third-party call, which breaks the offline and no-upload promise, and the
browser language is the better signal anyway.

A saved value that is no longer a shipped locale, or a storage that throws (private
mode), reads as "nothing saved". A failed write still switches the language for
the visit and is only lost on reload.

## How it is built

```
src/lib/i18n/
  shapes.ts    Locale (from project.inlang), LOCALE_NAMES (endonyms, never translated)
  hosts.ts     LocaleHost: localStorage, navigator.languages, <html lang>
  locale.ts    resolveLocale and changeLocale (Effects), matchLanguages (pure)
  state.ts     the active locale ref; overrides Paraglide's getLocale
  runtime.ts   ManagedRuntime with the live host
  fakes.ts     LocaleHost fake for tests
messages/      en.json, id.json
project.inlang/settings.json
src/paraglide/ generated, gitignored
```

Paraglide runs with `strategy: ["baseLocale"]` and does no detection or storage of
its own. `state.ts` calls `overwriteGetLocale`, so every `m.some_key()` reads the
locale ref. A message built before `state.ts` loads, for example a module-level
`m.*()` call, silently reads `en`. Build messages inside functions that run at render
or action time, never at module scope. The root route imports `state.ts`, so every
render and action sees the override.

The ref starts at `en` on the server and on the first client render, so the
prerendered shell and hydration match. The root layout resolves the real locale in
a layout effect that resolves synchronously and forces a render, before the first
paint.

`m.*()` calls are not reactive. The root layout calls `useLocale()`, which
re-renders the header and sidebar on a switch, and the page content is keyed on the
locale (`Fragment key={locale}` in `__root.tsx`). Switching language remounts the
current tool and drops what it was holding. The switcher is a settings action, so
this is accepted.

## Adding a string

1. Add the key to `messages/en.json` and `messages/id.json`. Names are
   `<area>_<element>`: `converter_title`, `common_download`. Shared text uses
   `common_`.
2. Run `bun run i18n` (also runs inside `typecheck`, `test` and the dev server).
3. Use it: `import { m } from "#/paraglide/messages.js"` and call `m.converter_title()`.

`bun run test` compiles first. A bare `vitest run` needs `src/paraglide`, so run
`bun run i18n` once on a fresh clone. `src/lib/i18n/messages.test.ts` fails when `id.json` lacks a key, has an extra
one, leaves a message empty or uses different `{parameters}` than `en.json`.

Do not build a sentence from fragments. Put the whole sentence in the message with
parameters, so each language controls its own word order. When a link or bold
text sits inside a sentence, split the message around it.

## The tool registry

`src/lib/tool-categories.ts` builds each `Tool` with `defineTool(id, ...)`. The
text fields (`label`, `blurb`, `keywords`, `seoTitle`, `seoDescription`, `crumb`) are
getters that read the `tool_<id>_*` messages, so every consumer keeps writing
`tool.label`. Pass the tool object itself around. Spreading it (`{ ...tool }`)
copies the getters' values once and freezes the language. A new tool needs six
messages in both catalogs: `label`, `blurb`, `keywords`, `seo_title`,
`seo_description` and `crumb`. The SEO test checks the length limits in every
language.

Page titles come from each route's `head()`, which the router runs on navigation.
The root layout calls `router.invalidate()` when the language changes so the
title and meta tags follow.

## Workers

Code in `src/workers/` runs in its own module graph. Its locale ref stays `en`
and `overwriteGetLocale` is never installed there, so an `m.*()` call inside a
worker is always English. Do not build user-facing text in a worker. Return a
tagged error or a result and build the message on the main thread, or pass the
locale in and call `m.some_key(params, { locale })`.

## Errors

A `Schema.TaggedError` takes its `message` from `m.*()` where it is created, so the
text is in the active locale at that moment. An error already on screen keeps its
language if the person switches.

## Numbers and dates

Format with the active locale: `toLocaleString(currentLocale())` and
`Intl.*(currentLocale(), ...)`, with `currentLocale` from `#/lib/i18n/state.ts`.
These calls are converted together with the sentence that contains them, in each
tool's translation PR, so an English sentence never carries an Indonesian number.

## Adding a language

Add it to `locales` in `project.inlang/settings.json`, add `messages/<code>.json`,
and add its name to `LOCALE_NAMES` in `shapes.ts`. The switcher lists every locale.

## Rollout

Translation lands in phases: the shell and search, then one PR per tool group
(Image, Video & Audio, File, Color, Developer). Until a tool's PR lands, its page
stays in English whatever the locale.

## Known limits

- Search engines see English only, because the URL does not carry the locale.
  Locale-prefixed URLs would touch the router, the prerender step, `sitemap.xml`,
  the canonical URLs in `src/lib/seo.ts` and the service worker's navigation
  fallback.
- The message-format plugin is installed from npm and read from `node_modules`
  (`project.inlang/settings.json`), so builds do not need the network.
